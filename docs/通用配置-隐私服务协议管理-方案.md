## 一、背景与目标

### 1.1 背景

当前后管没有任何协议内容的管理入口。隐私政策与用户服务协议的正文、版本、生效时间全部硬编码在 APP / H5 包里，导致：


| 问题        | 现状             | 后果                     |
| --------- | -------------- | ---------------------- |
| 版本号口径不统一  | 各端自己写死 `V2.1`  | 「隐私授权记录」里的版本号无法追溯到具体正文 |
| 变更弹窗靠临时开发 | 每次升版手写一个弹窗     | 修改隐私协议或服务协议需要发版        |
| 无留痕       | 谁改的、什么时候生效，无记录 | 监管问询 / 用户投诉时举不出证       |


行业标准做法：**协议升版时用一个阻断式弹窗告知变更点，用户勾选同意后才继续使用**。在基础协议场景中，我们需要把「弹窗 + 两份协议正文」作为一次**原子的发布**来管理；

### 1.2 目标

1. 协议正文、版本、生效范围全部后管可配，与 APP 发版解耦。
2. 以「发布记录」为原子单位，并按协议场景分开版本线：基础协议场景同时产出**隐私政策 + 用户服务协议 + 变更内容弹窗**；
3. 已发布记录**只读、不可删**，确保法律举证链完整；变更只能通过新增下一个版本实现。
4. 与「隐私授权记录」打通：用户在 APP 上点「同意」，落库的 `版本号` 精确指向本功能里的某一条发布记录。

## 二、核心概念

### 2.1 为什么以「发布记录」为主体，而不是以「协议」为主体

两种建模方式：


| 方案                 | 结构                              | 问题                                       |
| ------------------ | ------------------------------- | ---------------------------------------- |
| A. 协议为主体           | 隐私政策有自己的版本线，服务协议有自己的版本线         | 两份协议各自升版，版本号错位；变更弹窗不知道该关联谁；用户同意记录要存两个版本号 |
| **B. 发布记录为主体（采用）** | 一次发布 = 一个协议场景 + 一个版本号 + 该场景必需文档 | 同场景版本号唯一、生效时间唯一、举证链清晰                    |


**采用 B，但按协议场景隔离版本线。** 基础协议场景中，即使本次只改了隐私政策一个标点，用户服务协议正文也会被完整复制进新版本记录，也不会向全量老用户弹升版提示。

**协议场景值集（建议 `MYSANY.AGREEMENT_SCENE`）**


| 编码              | 名称        | 包含内容               | 触达时机      |
| --------------- | --------- | ------------------ | --------- |
| `PLATFORM_BASE` | 基础隐私/服务协议 | 隐私政策、用户服务协议、变更内容弹窗 | 首次启动或协议升版 |


### 2.2 基础协议发布记录的构成

```
发布记录  V2.1  ·  新加坡站点  ·  2026-10-15 00:00 生效
├── 隐私政策          【必填】 ← APP 端「我的-隐私政策」入口 & 弹窗内链接
├── 用户服务协议      【必填】 ← APP 端「我的-用户协议」入口 & 弹窗内链接
└── 变更内容弹窗      【必填】 ← 仅老用户升版时弹出一次，新用户不弹
```

**关键规则：变更内容弹窗不是协议。** 它是一次性的告知载体，用户点过「同意」后不再出现，APP 内也没有任何常驻入口可以再看到它。**最终在 APP 端长期可见的内容只有隐私政策和用户服务协议两份。** 这一点决定了弹窗正文的写法（只写"改了什么"，不写协议全文），也决定了它不参与协议详情页的路由。

## 三、状态机

```
        ┌──────────┐  保存草稿
   新建 ─►│ 草稿 DRAFT│◄───────── 编辑
        └────┬─────┘
             │ 提交发布
             ▼
   ┌──────────────────────┐
   │ 待生效 SCHEDULED      │  定时发布，未到生效时间
   └──────────┬───────────┘
              │ 到达生效时间（或"立即生效"直接进入）
              ▼
   ┌──────────────────────┐
   │ 已发布 PUBLISHED      │ ← 当前对外生效版本，同场景/站点/语言唯一
   └──────────┬───────────┘
              │ 被更新的版本取代
              ▼
   ┌──────────────────────┐
   │ 已失效 EXPIRED        │ ← 历史版本，永久留存供举证
   └──────────────────────┘
```

> **无审核环节。** 提交发布即进入 `SCHEDULED`（立即生效则直接进入 `PUBLISHED`），不设审核岗、不设驳回。协议合规由发布人自行负责。
>
> 基础协议与账户注销须知复用同一状态机，但在 `releaseScene` 维度分别计算「当前已发布版本」和版本取代关系。

### 3.1 状态定义（建议入值集 `MYSANY.AGREEMENT_RELEASE_STATUS`）


| 编码          | 名称  | 标签色 | 可编辑 | 可删除 | 说明                 |
| ----------- | --- | --- | --- | --- | ------------------ |
| `DRAFT`     | 草稿  | 默认灰 | ✅   | ✅   | 仅创建人与管理员可见         |
| `SCHEDULED` | 待生效 | 主色青 | ❌   | ❌   | 可「取消发布」退回草稿，取消须填原因 |
| `PUBLISHED` | 已发布 | 绿   | ❌   | ❌   | **终态之一，只读**        |
| `EXPIRED`   | 已失效 | 灰   | ❌   | ❌   | **终态之一，只读**        |


### 3.2 「已发布不可修改、不可删除」的落地细节

这是本方案的硬约束，需要在三个层面同时保证：

1. **UI 层**：`PUBLISHED` / `EXPIRED` 行的「编辑」「删除」按钮不是置灰，而是**不渲染**；点击行只进入只读详情页。
2. **接口层**：更新/删除接口对这两个状态直接返回业务异常，不依赖前端拦截。
3. **产品层**：提供「基于此版本新建」作为唯一的修改路径——复制该版本全部内容为新草稿，版本号自动 +0.1，创建人重新填写变更点。

**写错了怎么办？** 不提供删除，提供两条补救：

- 未到生效时间（`SCHEDULED`）→ 「取消发布」退回草稿修改，留痕；
- 已生效（`PUBLISHED`）→ 只能「基于此版本新建」发一个修正版，走正常流程。历史错误版本保留在列表里标记为已失效，这本身就是合规要求的一部分。

| Tab    | 必填  | 正文来源 | 字数上限   | 特殊字段               |
| ------ | --- | ---- | ------ | ------------------ |
| 隐私政策   | ✅   | 富文本  | 50,000 | 摘要（可选，用于 APP 折叠展示） |

## 五、关键业务规则

### 5.1 版本号

- 唯一性：同一「协议场景 + 站点 + 语言」下版本号不可重复（含已失效版本）。

### 5.2 生效与取代

- 同一「协议场景 + 站点 + 语言」在任一时刻**有且仅有一条** `PUBLISHED` 记录。
- 新版本生效的瞬间，旧版本自动置为 `EXPIRED`，并写入其「失效时间」。
- `SCHEDULED` 记录在同组合下可同时存在多条，但生效时间不可相同；建议前端在选择生效时间时校验冲突。

### 5.3 基础协议的弹窗触达规则（决定 APP 端行为，需与客户端对齐）


| 用户类型               | 是否弹窗                    |
| ------------------ | ----------------------- |
| 新用户（首次安装启动）        | **不弹变更弹窗**，走首次启动的隐私授权流程 |
| 老用户，已同意版本 < 当前生效版本 | **弹**，每个版本最多弹 1 次       |
| 老用户，已同意版本 = 当前生效版本 | 不弹                      |
| 老用户，上次点了「拒绝」       | 下次启动继续弹（直至同意或卸载）        |


> 不存在「静默更新」通道。每次协议升版都必须通过变更弹窗告知老用户，这是弹窗被定为必填项的直接原因。
>
> 弹窗内的两条勾选默认态由后管配置（合规建议默认不勾选）。**用户必须两条都勾选才能点「同意」**；只勾一条时「同意」按钮置灰。这样落库的授权记录才能分别证明两份协议各自获得了同意。

### 5.4 与「隐私授权记录」的联动

用户在弹窗点「同意」后，APP 上报一条授权记录，落入 `客户管理-隐私授权记录` 页：


| 授权记录字段 | 取值来源                                   |
| ------ | -------------------------------------- |
| 同意类型   | 固定写两条：`隐私协议` + `用户服务协议`；用户两条都勾选后2次上报   |
| 版本号    | 本发布记录的隐私协议或用户服务协议的版本号，如 `V2.1`         |
| 同意时间   | 客户端点击时间                                |
| APP/PC | 客户端上报（APP / PC）                        |
| 发布记录ID | `agreement_release.releaseId`，用于精确回溯正文 |
| 内容摘要   | 用户同意时协议正文的 SHA-256，防止仅靠版本号举证           |


点「拒绝」同样上报，记录同意类型为空、动作为 `REJECT`，用于统计拒绝率。**「同意」要求两条勾选齐全**，因此不会出现"只同意了其中一份协议"的记录。



> 原「四眼原则（提交人不可审核自己提交的版本）」随审核机制一并取消。协议合规由发布人自负，系统只保证**发布留痕**与**已发布不可改**两条硬约束，监管问询时可通过操作日志完整回溯。若后续合规要求恢复审核，按 §3 状态机加回 `REVIEWING` 即可，其余结构不受影响。

### 5.7 多站点与多语言

- 「适用站点」可多选，一次发布同时对多个站点生效——适用于各站点协议正文一致的场景。
- 「语言」单选。同一批内容的多语种，通过「基于此版本新建 → 改语言 → 替换正文」创建，版本号保持一致（此时版本号唯一性约束为「协议场景+站点+语言」维度，故不冲突）。
- APP 按「协议场景 + 用户所在站点 + 系统语言」匹配生效版本；匹配不到时**回落到该场景、该站点的英文版本**，仍匹配不到则回落到简体中文版本。若 `ACCOUNT_CANCELLATION` 在所有回落语言下都无已发布版本，APP 必须阻止提交注销并提示联系客服，不得在无须知的情况下生成申请。

## 七、异常与边界


| 场景               | 处理                                       |
| ---------------- | ---------------------------------------- |
| 编辑中断网 / 关页面      | 每 30 秒自动存本地草稿，重进时提示「检测到未保存内容，是否恢复」       |
| 两人同时编辑同一草稿       | 乐观锁，后提交者报「内容已被他人更新，请刷新」                  |
| 定时发布到点时服务异常      | 定时任务重试 3 次，仍失败则置为异常态并告警给发布人              |
| 弹窗标题 / 正文为空      | 提交发布前强校验并自动切到「变更内容弹窗」Tab，拦截提交            |
| 富文本粘贴进 Word 的脏样式 | 编辑器强制过滤 `style` 白名单外属性，仅保留基础排版标签         |
| 发布编号与已失效发布编号重复   | 提交时校验拦截，提示「VS20261008 已于 2026-08-01 使用过」 |
| 协议正文为空           | 提交发布前强校验，自动切到对应 Tab 并提示                  |

## 八、埋点与度量


| 指标       | 口径                 | 用途            |
| -------- | ------------------ | ------------- |
| 弹窗曝光量    | 按版本号 / 站点          | 分母            |
| 同意率      | 同意数 / 曝光量          | 低于 90% 需复核文案  |
| 拒绝率      | 拒绝数 / 曝光量          | 高拒绝率 = 文案引起恐慌 |
| 平均阅读时长   | 弹窗停留时长中位数          | < 2 秒说明用户在盲点  |
| 协议详情页 PV | 按文档类型              | 评估是否需要摘要折叠    |
| 覆盖进度     | 已同意最新版本用户数 / 活跃用户数 | 合规整改的完成度      |
